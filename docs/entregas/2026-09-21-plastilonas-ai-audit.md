# Auditoría — cimientos para "Plastilonas AI" (Fase 0, solo lectura)

**Rama:** `feat/plastilonas-ai-asistente` (base `main` @ `83796c6`)
**Fecha:** 2026-09-21
**Alcance:** inventario del código existente que las fases siguientes (núcleo de IA / tools, posible `/asistente`) deben **reutilizar**, no recrear. Esta fase no escribió código de producto ni tocó esquemas; es un mapa.

El sitio ya tiene un asistente de chat funcional (Claude vía Vercel AI SDK, `app/api/chat/route.ts` + `components/Chatbot.tsx`), un flujo de RFQ completo con persistencia opcional en Supabase, checkout de Stripe, Auth.js v5 con degradación segura, y ~19 libs de dominio que ya son la fuente de verdad para productos, cifras, calculadoras, guías, industrias, etc. La brecha principal para una "Fase 1 de IA" no es la data ni el chat en sí — es que el chat de hoy es **un único prompt de sistema con catálogo embebido en texto**, sin *tool calling* estructurado contra esas libs, y sin memoria/contexto de sesión más allá de los mensajes en curso.

## Gaps — lo que la Fase 1 (núcleo de IA / tools) tiene que construir desde cero

1. **No hay tool calling / function calling en el chat.** `app/api/chat/route.ts` usa `streamText` sin `tools:`. Todo el conocimiento de producto vive como texto plano inyectado en el `system` prompt (`CATALOG`). Fase 1 debe introducir tools tipadas (Zod) que envuelvan `lib/products.ts`, `lib/calculadoras.ts`, `lib/glosario.ts`, etc., en vez de seguir agrandando el prompt.
2. **No hay memoria de conversación persistente ni por-usuario.** El `useChat` del widget solo mantiene estado en memoria del cliente durante la sesión del navegador; no se guarda en Supabase ni se asocia a una sesión de Auth.js. Si Fase 1 quiere "recordar" un RFQ a medio hacer entre visitas, hay que diseñarlo — hoy no existe.
3. **No hay endpoint de "generar cotización" invocable por el asistente.** El chat solo *sugiere* ir a `/cotizacion?origen=chat`; no hay una tool que llame a `/api/lead` directamente desde una conversación de IA. Construir esa tool implica decidir qué campos puede completar el modelo sin inventar datos (nombre, email, teléfono deben venir del usuario, no del LLM).
4. **`lib/indicadores.ts` existe pero no fue parte de los 15 libs de dominio listados en el encargo** (confirmado: `ls lib/indicadores.ts`) — Fase 1 debería auditarlo aparte si planea una tool de indicadores de mercado, ya que hoy no tiene reuse plan documentado aquí.
5. **Sin política de Storage documentada para `rfq-adjuntos`.** El bucket se referencia en código (`CotizacionForm.tsx`) pero no se auditaron sus políticas RLS ni límites (fuera de alcance de esta fase, que no toca esquemas) — señalarlo para quien diseñe una tool de "adjuntar archivo" en el asistente.
6. **`/proyectos` es solo listado, sin ruta dinámica `[slug]`.** Confirmado: `app/(es)/proyectos/` solo contiene `page.tsx` y `layout.tsx`, no `[slug]`. Una tool de IA no puede enlazar un proyecto individual por URL propia hoy — solo puede referir a `/proyectos` en general, y solo mencionar los que `lib/projects.ts#projectsPublicados` marca como `verificado: true`.
7. **No hay separación de "modo asistente" (`/asistente`) del chatbot flotante.** Esto es intencional en esta fase (prohibido crear la ruta), pero se deja constancia de que hoy solo existe el widget flotante — cualquier página dedicada de Fase 2 debe reusar `app/api/chat/route.ts` y `lib/chat/intents.ts`, no duplicar lógica.
